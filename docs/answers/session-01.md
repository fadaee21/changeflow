# پاسخ‌های جلسهٔ اول

## سؤال ۱

1. پاس شدن تست‌ها فقط نشان می‌دهد برنامه فعلاً درست کار می‌کند. ولی اگر منطق اصلی داخل Controller باشد، ساختار پروژه درست نیست.

2. قانون جدا بودن مسئولیت‌ها باید در Constitution باشد، چون برای کل پروژه است. در Plan روش انجام آن نوشته می‌شود و در Tasks کارهای کوچک‌تر مشخص می‌شوند.

3. برای جلوگیری از تکرار این مشکل، این قانون را در Constitution می‌نویسیم و در زمان بررسی کد چک می‌کنیم که منطق اصلی داخل Controller نباشد.

## سؤال ۲

1. نه، Agent نباید این تصمیم را بدون تأیید مالک محصول نهایی کند؛ چون یک قانون مهم است و باید سؤال کند یا آن را به‌عنوان ابهام ثبت کند.

2. Assumption یک فرض موقت است که هنوز تأیید نشده و ممکن است تغییر کند. اما تصمیم تأییدشدهٔ مالک محصول یک نیازمندی قطعی است و باید در Artifactها ثبت و در پروژه اجرا شود.

3. آیا مدیر می‌تواند درخواست را رد کند یا برای اصلاح برگرداند؟ آیا می‌تواند کامنت بگذارد؟

4. اگر تأیید درخواست با خطا مواجه شود، وضعیت درخواست چه می‌شود؟

## سؤال ۳

1. Requirement این است که هیچ درخواست تأییدشده‌ای با محتوای تغییرکرده، بدون تأیید دوباره اجرا نشود. ایجاد فیلد `ContentRevision` یک Design Decision است؛ چون فقط یکی از راه‌های پیاده‌سازی این Requirement است.

2. چون برای انجام این Requirement چند راه فنی وجود دارد، بهتر است قبل از پیاده‌سازی در Plan/Research گزینهٔ مناسب بررسی و انتخاب شود.

3. دو راهکار:

   - **قفل‌کردن درخواست پس از تأیید**: بعد از `Approved` شدن، امکان ویرایش محتوا وجود نداشته باشد. مزیت آن ساده بودن است و عیب آن این است که برای تغییر جدید باید یک درخواست جدید ثبت شود.
   - **ذخیرهٔ نسخهٔ تأییدشده**: یک کپی از محتوای تأییدشده نگه داریم و قبل از اجرا آن را با محتوای فعلی مقایسه کنیم. مزیت آن مشخص بودن محتوای تأییدشده است و عیب آن نیاز به فضای بیشتر و پیاده‌سازی کمی سخت‌تر است.

## سؤال ۴

1. Taskها باید ترتیب درست داشته باشند. Analyze بررسی می‌کند کدام Taskها به هم وابسته‌اند و کدام Taskها را می‌توان به‌صورت موازی انجام داد.

2. Analyze بررسی می‌کند ترتیب Taskها درست است یا نه، کدام Taskها به هم وابسته‌اند و کدام‌ها را می‌توان هم‌زمان انجام داد. همچنین اگر ترتیب اشتباه یا تداخل بین Taskها وجود داشته باشد، آن را گزارش می‌کند.

3. خیر. پوشش همهٔ Requirementها کافی نیست، چون ممکن است ترتیب Taskها اشتباه باشد یا Taskهای موازی با هم تداخل داشته باشند. Taskها باید قابل اجرا و بدون وابستگیِ حل‌نشده باشند.

## سؤال ۵

1. خیر، چون یک قانون امنیتی رعایت نشده و یک معیار پذیرش انسانی هنوز بررسی نشده است. پس Feature هنوز کامل و قابل‌پذیرش نیست.

2. Build یعنی پروژه بدون خطا ساخته شود. Test یعنی بخش‌های برنامه با تست بررسی شوند. Validation یعنی بررسی کنیم برنامه نیازمندی‌ها و قوانین پروژه را رعایت کرده است یا نه. Acceptance یعنی مالک محصول تأیید کند که Feature برای استفاده مناسب است.

3. Analyze قبل از پیاده‌سازی، Spec، Plan و Tasks را بررسی می‌کند. Converge بعد از پیاده‌سازی، کد را با Spec و Plan مقایسه می‌کند و اگر چیزی کم باشد، آن را به Task جدید تبدیل می‌کند.

4. اگر Converge شکاف پیدا کند، آن را به Task جدید تبدیل می‌کنیم. سپس در صورت نیاز Plan را اصلاح می‌کنیم، Task را اجرا می‌کنیم و دوباره Validation انجام می‌دهیم. اگر Spec یا Plan تغییر کند، Analyze هم دوباره اجرا می‌شود.
